The basics

What is a JSONL to CSV converter?

A JSONL to CSV converter turns JSON Lines into CSV. JSON Lines (also called .jsonl, .ndjson, or newline-delimited JSON) is a format where every line of the file is one complete, self-contained JSON value. No wrapping array, no commas between records — just one record per line.

That format shows up everywhere: application logs, event streams, message-queue dumps, model training datasets, database change-data-capture exports, and the output of most command-line tools that emit structured records. It is deliberately streamable — you can process a 10 GB file one line at a time without loading it all into memory.

CSV is the other half of the equation. It is the format every spreadsheet, BI tool, and database bulk loader understands. Converting JSONL to CSV turns a machine-readable stream into something you can filter, pivot, and chart in Excel without writing a single line of code.

HopConvert handles the messy parts: it reads each line independently, unions the keys across every record so sparse records still line up, flattens nested objects into columns like props__device, joins arrays of primitives with | , and skips (and reports) any line it cannot parse instead of failing the whole file. And it does all of it in your browser — the file is never uploaded anywhere.

What exactly is JSON Lines?

JSON Lines (also written jsonl, ndjson, or newline-delimited JSON) is a text format in which each line is one complete and independent JSON value. There is no enclosing array and no comma between records. The format was popularised by the creators of jsonlines.org and is now used by Elasticsearch, MongoDB, CouchDB, BigQuery, and most modern log shippers.

A minimal example:

{"id": 1, "event": "page_view", "user": "alice"}
{"id": 2, "event": "purchase", "user": "bob", "amount": 49.99}
{"id": 3, "event": "signup", "user": "carol"}

Notice that each record carries its own id. That redundancy is the point: every line stands alone, so a reader can process, route, or discard it individually. A JSON array of the same three records would need to be opened, scanned, and closed as one unit, and a single syntax error anywhere would break the entire file.

JSONL or a JSON array?

These hold the same information but behave very differently:

  • A JSON array is a single document. It must be valid from the first [ to the last ]. You cannot append to it without rewriting it, and a truncated file is unparseable.
  • JSON Lines is a stream. Records are appended as they arrive, consumers read them one at a time, and a damaged line only affects that line.

That is why almost every log pipeline, event bus, and streaming database uses JSONL. When you convert JSONL to CSV, you are essentially freezing a stream into a table.

What shape is the output?

The converter produces a standard CSV: one header row of column names, then one row per record. Column names come from the union of the keys across every record, so if record 4 has a plan field that the first three do not, plan becomes a column and the other rows get an empty cell in it.

CSV output uses CRLF line endings and RFC 4180 quoting: any field containing a comma, a double quote, or a newline is wrapped in double quotes with inner quotes doubled. Values are written as text, which is exactly what spreadsheets expect.

How is nested data handled?

JSONL records are often not flat. The converter offers two strategies:

  • Header / detail (default): A nested object such as {"id": 1, "props": {"device": "mobile"}} is flattened into two columns: id and props__device. The separator is configurable in settings.
  • Flatten: The same result, but with nested arrays of objects also flattened into wider columns rather than expanded into extra rows.

Arrays of primitive values — tags, skills, categories — are joined with | so they stay readable in a single cell. Arrays of objects become one row per element with the parent fields repeated, which is the classic header/detail layout your BI tool expects.

What about records with different keys?

This is the normal case, not an edge case. Event streams are sparse by design: a purchase event carries an amount, a page_view does not. The converter builds the column set from every record it reads, so all rows share the same columns and missing values are simply blank.

This is also why column order is derived from first appearance rather than sorted alphabetically — the first record in the file decides the leading columns, which usually matches the order the producer writes them in.

Common edge cases

  • Malformed lines: Skipped and reported with their line numbers. The rest of the file still converts.
  • Blank lines: Ignored entirely.
  • UTF-8 BOM: Detected and stripped from the first line.
  • CRLF and LF endings: Both parse correctly, even if mixed within one file.
  • Top-level arrays per line: If a line holds a JSON array instead of an object, it is treated as a single record and stringified into one cell.
  • Very long lines: There is no line-length limit; only your tab's memory is the constraint.
  • Duplicate keys within one line: The last occurrence wins, matching JSON.parse behaviour.

Using JSONL in a real pipeline

A common end-to-end flow looks like this:

curl -s https://api.example.com/events.jsonl \
  | jq -c 'select(.status != 200)' \
  | ./hopconvert-jsonl-to-csv \
  > errors.csv

Or, entirely in the browser, using the filter box on the converter:

select(.event == "purchase")

That filter keeps only purchase events. Combine it with a path such as .props to convert just the nested payload into columns.

For very large files, remember that conversion happens in your browser — the practical ceiling is your tab's available memory. Close other tabs, use a 64-bit browser, and expect roughly 50 MB per second of throughput on a modern laptop.

What is a JSONL to CSV converter?
A JSONL to CSV converter reads a JSON Lines file — one complete JSON value per line — and writes a standard CSV table with a header row and one row per record. It is the fastest way to turn an event stream, log dump, or dataset into something Excel, Google Sheets, or a BI tool can read.

What is the difference between JSONL and NDJSON?
None in practice. JSON Lines and NDJSON are two names for the same thing: one JSON value per line. The extensions .jsonl and .ndjson are used interchangeably, and HopConvert accepts both.
Can I paste a regular JSON array instead?
Yes. If your input starts with [, the converter parses it as a standard JSON array and converts it the same way. That makes it easy to use this tool as a general JSON-to-CSV converter.
What happens if a line is not valid JSON?
That line is skipped and reported with its line number, and the rest of the file still converts. You will see a note above the preview telling you exactly which lines were skipped so you can go fix the source.
How do I convert nested objects in JSONL?
Nested objects are flattened into columns named parent__child by default — for example props.device becomes props__device. You can change the separator in settings, or switch to the flatten strategy to widen arrays of objects too.
What is the maximum file size?
There is no hard limit. Because conversion happens in your browser, the practical limit is the memory available to your tab (typically 200 MB to 2 GB). For files over 100 MB, use Chrome or Edge on a 64-bit system and close other tabs.
Can I filter records before converting?
Yes. The filter box accepts a small jq-style expression, for example select(.event == "purchase") or .props. It runs entirely in your browser and updates the preview as you type.
